# B17. Потоки в Wasm

**Сравнивали.** Разбор всех 131 тайла фикстур (распакованных заранее) полным парсером при одинаковом числе потоков (7, ядра минус один):
- 7 воркеров, у каждого свой экземпляр Wasm воркера карты (решение движка, без SharedArrayBuffer), тайлы раздаются по кругу;
- один экземпляр Wasm с общей памятью и пулом rayon из 7 потоков (`wasm-bindgen-rayon`, nightly Rust с atomics и пересобранной std, требует COOP/COEP). Код: `crates/bench-rayon`, сборка `scripts/build-rayon.sh` (вне проверок stable);
- тот же экземпляр с пулом из одного потока: цена самой сборки с общей памятью без конкуренции потоков.

Метрика — время на весь набор и тайлов в секунду. Код: `apps/playground/src/bench/threads*.ts`, страница `bench-threads`.

**Окружение.** Mac пользователя (8 логических ядер), Chrome 157 headless, cross-origin isolation включена.

| путь | набор, мс (медиана) | p95 | тайлов в секунду |
|---|---|---|---|
| **7 воркеров, по экземпляру Wasm** | **337** | **342** | **389** |
| общий экземпляр, пул rayon из 7 | 8027 | 8220 | 16 |
| общий экземпляр, пул rayon из 1 | 1411 | 1423 | 93 |

Сырые данные: `raw/bench-threads-2026-11-21-18-56.json` и прогон с 8 проходами `raw/bench-threads-2026-11-21-18-55.json`.

**Решение: несколько воркеров со своим Wasm, как сейчас.** Пул rayon на одной памяти медленнее одного своего потока: парсер много выделяет память, а аллокатор std для wasm32 с atomics — один глобальный замок, за который потоки дерутся. Воркеры с отдельной памятью этого не знают и масштабируются почти линейно. К тому же им не нужен SharedArrayBuffer, а значит COOP/COEP на сайте клиента. Ветку с rayon не берём даже как дополнительный режим.
