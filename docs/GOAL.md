# Цель: полный перенос ImmersiveMap в браузер

## 1. Что нужно получить

Браузерную библиотеку карты `@immersive-map/web` с теми же возможностями, что у Swift-движка ImmersiveMap (`~/Desktop/ImmersiveMap`): глобус, который непрерывно разворачивается в плоскую карту, подписи, здания с тенями, рельеф, данные приложения (слои), аннотации, pins, 3D-модели, выделение, экспорт снимков и видео. Карта должна работать с теми же данными: тот же архив PMTiles (`https://tiles.immersivemap.dev/20260922.pmtiles`), тот же архив моделей, те же атласы шрифтов, тот же overview-архив.

Главный критерий — **максимальная производительность**. Второй — **только современные технологии**. Совместимость со старыми браузерами не нужна.

Готово, когда выполнены все пункты раздела 9 «Критерии готовности».

## 2. Исходные данные

- **Эталон:** `~/Desktop/ImmersiveMap`, только для чтения. Ничего в нём не менять, не коммитить и не запускать там тесты.
  - `CLAUDE.md` содержит архитектурные решения, которые код не показывает. Прочитать целиком до начала работы.
  - `.claude/rules/*.md`: публичный API и стиль, кэш подготовленных тайлов, MVT, тесты.
  - `Documentation/*.md`: что умеет карта с точки зрения пользователя. Это список функций, который надо перенести.
  - `Sources/`: около 89 тыс. строк Swift и 3,9 тыс. строк MSL. Комментарий на главном типе каждой папки описывает её границы.
  - `Tests/`: около 230 файлов тестов. Тесты на чистую логику переносятся вместе с кодом.
- **Целевой репозиторий:** `~/Desktop/ImmersiveMapWeb`. Прототип уже есть, см. `README.md`:
  - Rust-крейты `pmtiles`, `mvt`, `tile-prep`, `worker-wasm`, `bench-wgpu`;
  - TS-пакет `packages/immersive-map` (пул воркеров, рендер на WebGPU, плоская карта);
  - демо-страница `apps/playground`;
  - скрипт `scripts/probe.mjs` (headless Chrome: снимок экрана, статистика, бенчмарк).

## 3. Стек (решено)

| Слой | Технология |
|---|---|
| GPU | WebGPU, только он. WGSL-шейдеры, перенесённые с MSL вручную |
| Вычисления | Rust → `wasm32-unknown-unknown`, SIMD128, wasm-bindgen, wasm-opt |
| Рендер-слой и API | TypeScript (strict), прямые вызовы WebGPU |
| Потоки | Web Workers, у каждого свой экземпляр Wasm, передача через transferable `ArrayBuffer` |
| Сборка | Cargo, Vite 8 (library mode и playground), npm workspaces, ESM |
| Тесты | `cargo test`, Vitest, Playwright (системный Chrome, WebGPU) |

Что уже измерено в прототипе (headless Chrome, Mac пользователя):
- Команды WebGPU, записанные из Rust через `wgpu`, на 10–80% медленнее прямых вызовов из TS. **Рендер-слой пишем на TS.** `crates/bench-wgpu` остаётся только как бенчмарк.
- Render bundle стоит около 0,03 мс при любом числе вызовов отрисовки. Статичные проходы строим на bundles.
- Подготовка тайла z14 (центр Москвы) в Wasm: медиана 3 мс, максимум 14 мс. Wasm воркера около 33 КБ в brotli.

Включаем все доступные опциональные возможности WebGPU и проверяем их наличие при старте: `shader-f16`, `clip-distances`, `depth32float-stencil8`, `timestamp-query`, `texture-compression-bc`, `texture-compression-astc`, `float32-filterable`. Без возможности, которая нужна, работает запасной путь внутри WebGPU, а не WebGL.

## 4. Обязательное правило: замеры там, где неясно, что быстрее

Если у задачи есть два и больше разумных способа решения и заранее неизвестно, какой быстрее, **решение принимается только по замеру**.

### Как мерить

1. Бенчмарк лежит в репозитории: `bench/` для Rust (criterion или собственный harness с `std::time`), `apps/playground/bench-*.html` для браузерных. Его можно перезапустить одной командой.
2. Данные фиксированные: набор реальных тайлов скачивается один раз скриптом `scripts/fetch-fixtures.sh` в `fixtures/` (папка в `.gitignore`). Минимум в набор входят:
   - центр Москвы и Манхэттен на z14–15;
   - Альпы (Церматт) на z10–13, с рельефом;
   - глобус на z0–5;
   - пустой океанский тайл.
   Бенчмарк не ходит в сеть.
3. Браузерные замеры идут в Chrome с cross-origin isolation (COOP `same-origin`, COEP `credentialless`), иначе у `performance.now()` разрешение 0,1 мс. Перед замером прогрев, затем не меньше 50 итераций. Записываются медиана и p95.
4. Сравниваются полные пути, а не их части. Например, «Rust против TS» включает переход через границу Wasm/JS и копирование данных.
5. Результат записывается в `docs/benchmarks/<тема>.md`:
   - что сравнивали;
   - машина и версия браузера;
   - таблица с цифрами;
   - решение и почему.
   Выбранный вариант остаётся в коде, проигравший удаляется. Бенчмарк остаётся.
6. **Правило выбора:** если разница меньше 10% или в пределах шума, берём более простой вариант. Если вариант быстрее, но требует от сайта клиента особых условий (например, COOP/COEP для SharedArrayBuffer), он может быть только дополнительным режимом, не основным.

## 5. Архитектура

Архитектуру Swift-движка сохраняем, если замер не требует иного. Главные решения из `CLAUDE.md` эталона:

- **Зависимости направлены внутрь:** UI → Render и папки функций → Utils. Каждая функция владеет своей моделью, математикой, шейдерами и рендер-подсистемой. Render знает функцию только через интерфейс подсистемы.
- **Схема и стиль разделены:** схема говорит, *что это за объект*, стиль — *как его рисовать*. Логика конкретной схемы (Protomaps) не попадает в Render, Tile и Labels. Отпечаток стиля входит в ключ дискового кэша.
- **Отрисовка по запросу:** кадр рисуется только при изменении состояния, активности (жест, анимация, затухание) или явном запросе.
- **Глобус и плоская карта — одно непрерывное превращение** по значению от 0 до 1 в шейдерах, а не переключатель.
- **Тайлы показываются одним механизмом на обеих поверхностях:**
  - планировщик (`TilePlacementPlanner`) решает, что показывать, и помнит прошлый кадр;
  - проход-разметка пишет в стенсил зум источника, а земля рисуется по равенству;
  - на рельефе тайл ставится только вместе со своим террейном.
  Прототипный scissor заменяется этим механизмом.
- **Рельеф не рисует ничего своего:** он меняет то, как рисуют другие. Ядро — хранилище террейна и состояние кадра, а рельеф каждой функции лежит в папке этой функции.
- **Модель заменяет здание в кадре, а не при разборе** (`TileBuildingRange`, `HiddenBuildingIndexBuffers`, `ReplacedBuildings` по зуму).
- **Overview-архив** (`overview.pmtiles`, 5,5 МБ: биомы, озёра, дороги Natural Earth) склеивается с тайлами z0–7 побайтово и поставляется в npm-пакете как ассет.
- **Настраиваемое значение — это настройка API, а не константа.** Это правило «setting, not constant» из эталона.

Разделение по языкам:
- **Rust (Wasm):** форматы (PMTiles, MVT, формат тайла моделей), разбор тайлов и всё, что победит в замерах B1, B4, B9–B11, B14.
- **TypeScript:** публичный API, DOM (аннотации, бейдж атрибуции, панель отладки), ввод, сеть, оркестрация воркеров, весь код, вызывающий WebGPU.
- Граница между ними: плоские бинарные буферы (арена тайла, как `PreparedTileArenaImage` в Swift), без объектов JS на каждый элемент.

Структура репозитория расширяется по образцу эталона, по папкам функций:
- Rust: `crates/<формат-или-функция>`;
- TS: `packages/immersive-map/src/<функция>/` с шейдерами WGSL внутри функции.

## 6. Публичный API

Ванильный TypeScript-класс. Модификаторы SwiftUI становятся опциями и сеттерами:

```ts
const map = await ImmersiveMap.create({
  container,
  settings: ImmersiveMapSettings.default.night().shadows({ strength: 0.6 }),
  camera: { city: "paris", zoom: 15 },
});
map.setSettings((s) => s.groundRelief({ isEnabled: true }));
map.camera.fly({ center: [2.2945, 48.8584], zoom: 16, pitch: 1 });
map.pins.set([...]);
map.layers.register("districts", { geoJSON: url });
map.on("pinTap", (event) => {});
```

- Настройка задаёт только переданные значения, остальные не трогает. Это правило модификаторов эталона.
- Контроллеры сохраняют смысл Swift-версии: camera (jump, fly, follow, tour), pins, layers, sceneModels, selection.
- Изменения, требующие повторной подготовки тайлов (источник, стиль, подписи, кэши, pins, архив моделей, MSAA), пересобирают карту так же, как в Swift.
- Пользовательский стиль и схема: решить замером, как они работают в воркере на Rust. Варианты: декларативное описание (JSON-правила), которое исполняет Rust, или JS-функция в воркере на каждый объект. Добавить строку B19 в таблицу замеров.
- React-обёртку **не делать** в рамках этой цели.

## 7. Что перенести: функции по этапам

Каждый этап заканчивается рабочей демо-страницей, перенесёнными тестами логики и снимками экрана для человека (раздел 8). Порядок обязателен: каждый этап опирается на предыдущий.

### Этап 0. Основа
- Фикстуры (`scripts/fetch-fixtures.sh`) и инфраструктура бенчмарков (раздел 4).
- Vitest, Playwright-смоук в системном Chrome, CI-скрипт `npm run check` (typecheck, `cargo test`, `cargo clippy -D warnings`, Vitest).
- Замеры B1, B2, B3, B12.

### Этап 1. Тайлы и плоская карта
- Загрузчик: дедупликация, приоритет по расстоянию до центра, повторы при ошибках, отмена, ETag архива.
- Дисковый кэш подготовленных тайлов: ключ — источник + отпечаток стиля + версия формата.
- Схема Protomaps (`Schema/Default`, `VectorTileAdaptation`) и встроенный стиль с темой (`Style/Default`): дневная и ночная палитры, цвета глобуса, `labelOpacity` по зуму.
- Разбор полностью как в Swift:
  - полигоны с flattening (`TileFlattening`);
  - линии с антиалиасингом и пунктиром;
  - дороги: уровни, тоннели и мосты, обводка, продолжения, сшивка улиц;
  - здания с подъёмом по высоте.
- Планировщик и стенсил-приоритет источников, запасные тайлы при загрузке.
- Камера: центр, зум, азимут, наклон; ограничения и границы; отрисовка по запросу и темп кадров.
- Жесты: перетаскивание с инерцией, колесо и pinch к точке, поворот двумя пальцами, наклон (правая кнопка или Alt + перетаскивание, два пальца вверх-вниз), чувствительность наклона.
- Overview-архив для z0–7.
- Замеры B4 (планировщик), B5, B6, B7, B18.

### Этап 2. Глобус и сцена
- Сфера, разворачивающаяся в плоскость (`Globe/`), горизонт и атмосфера (`Horizon/`), звёзды с затуханием, прозрачный космос.
- Освещение глобуса: подсолнечная точка, ночная сторона.
- Небо, туман и наземный туман (`GroundFog/`).

### Этап 3. Подписи
- Атлас SDF и раскладка текста (`Text/`): переносы, выравнивание, трекинг, обводка (halo).
- Подписи населённых пунктов и районов, POI со спрайтами, подписи вдоль дорог, подписи на поверхности, щиты маршрутов.
- Решатель коллизий, затухание, язык подписей.
- Замеры B4 (подписи), B13.

### Этап 4. Здания, деревья, тени, сглаживание
- Экструзия зданий с анимацией подъёма, деревья (модель `tree_broadleaf.immtree`, рассыпка), солнце сцены.
- Теневые карты с повторным использованием, тени от зданий, деревьев и моделей.
- MSAA и FXAA.
- Замеры B15, B16.

### Этап 5. Рельеф
- Источник террейна (Mapterhorn по умолчанию, кодировки terrarium и mapbox), хранилище и кэш выгруженных тайлов.
- Смещение сетки земли, затенение склонов, затенение долин.
- Появление и исчезновение по зуму, решение о схлопывании, когда террейна нет (404).
- Подъём дорог, зданий и подписей вместе с землёй. Камера над хребтами с запасом высоты.
- Горный туман, событие «горы или равнина» (`onTerrainSurroundingsChange`).
- Замеры B9, B10.

### Этап 6. Данные приложения
- Слои (`Layers/`): источники из GeoJSON и из фигур в коде, identity, простой стиль из свойств GeoJSON (simplestyle), стили полигонов, линий и точек, диапазоны зума.
- Показ и скрытие, обновления, лимит памяти, дисковый кэш мешей.
- Линии всегда сплошные и без смешивания, как решено в эталоне.
- Аннотации: DOM-элементы на координатах, исчезают за горизонтом глобуса, точка привязки, порядок.
- Pins: рамки (`bubble`, `circle`, `roundedRectangle`, `picture`, маска, путь), удалённые картинки с заглушкой, приоритет, группы (`merge`/`unmerge`), раздвигание pins при коллизиях, неподвижные pins.
- Нажатия и выделение: pins, модели, фигуры слоёв, общий интерфейс выбираемой функции.
- Бейдж атрибуции: кредиты по зуму, ссылки, внешний вид, скрытие с явным подтверждением.
- Замеры B4 (pins), B8, B11.

### Этап 7. 3D-модели
- Архив моделей: формат тайла модели версии 6, порт `ModelTileFormat`. Загрузка по видимым тайлам, бюджеты памяти и диска, depth bias, скрытие заменённых зданий.
- Свои модели: в браузере вместо USDZ формат **glTF 2.0 / GLB** (плюс OBJ, как в эталоне). Размещение, ориентация, анимация изменений, полёт по пути, нажатия.
- Замер B14. **Формат архива моделей не менять:** это контракт с опубликованными архивами и внешним бейкером. Если замер покажет, что нужен другой формат текстур, остановиться и спросить пользователя.

### Этап 8. Анимации камеры и экспорт
- Перелёты (`fly` с `overviewFirst`), следование по пути, туры, список городов (`ImmersiveMapCity`), снимок камеры, события изменения камеры и начала взаимодействия.
- Экранные элементы управления: панель камеры, зоны наклона и зума для сенсорных экранов.
- Снимок: рендер вне экрана в `Blob`/`ImageBitmap`, ожидание тайлов (settle timeout), повторяемость (`sceneDate`), пресеты размеров (`ImmersiveMapFrameFormat`).
- Видео: тур кадр за кадром через WebCodecs `VideoEncoder` (H.264, HEVC, AV1 — что доступно в браузере), MP4 через Mediabunny, прогресс, отмена. Аннотации и pins рисуются в кадр.
- Событие отрисованного кадра со счётчиками ожидания тайлов.

### Этап 9. Панель отладки
- Аналог `ImmersiveMapDebug`: HUD с тайлами, временем CPU и GPU, переключателями и кривыми настроек, экспортом настроек.
- Отдельная точка входа пакета (`@immersive-map/web/debug`), которая не попадает в основной бандл.

## 8. Как проверять

- **Тесты логики** переносятся из `~/Desktop/ImmersiveMap/Tests` вместе с кодом: Rust-логика в `cargo test`, TS-логика в Vitest. Правила эталона из `.claude/rules/tests.md` действуют и здесь:
  - тесты не ходят в сеть, данные только из фикстур или локального сервера;
  - нет тестов, которые сравнивают пиксели;
  - нет тестов «подождать N мс и проверить»;
  - нет тестов вёрстки DOM.
- **Форматы** (PMTiles, MVT, тайл модели) проверяются кодировщиком для тестов, независимым от декодера, как в эталоне.
- **Смоук в браузере:** Playwright открывает каждую демо-страницу в Chrome и проверяет, что нет ошибок WebGPU и исключений, что тайлы загрузились и кадр отрисован.
- **Внешний вид оценивает человек.** На каждом этапе сохраняются снимки в `docs/screenshots/<этап>/` для тех же видов, что в README эталона (`Tools/ReadmeFrames/frames.json`): глобус над Европой, Маттерхорн, Манхэттен, Рим, Кремль и другие. Агент сравнивает их с картинками из `Assets/` эталона сам и записывает, что отличается.
- **Производительность на каждом этапе** записывается в `docs/benchmarks/progress.md` на одном и том же маршруте камеры (скриптовый облёт Москвы, Манхэттена и Альп):
  - время кадра CPU и GPU, медиана и p95;
  - время до первого полного кадра;
  - размер бандла.
  Регрессия больше 10% без объяснения — ошибка, которую надо исправить.

## 9. Критерии готовности

1. Всё из раздела 7 работает на демо-страницах, и каждая страница `Documentation/` эталона имеет аналог в `docs/guide/` с примерами на TS API.
2. Все замеры из раздела 4 выполнены и записаны с решением. Оставлены только выигравшие варианты.
3. `npm run check` проходит без ошибок и предупреждений. Смоук Playwright проходит.
4. На облёте из раздела 8 карта держит 60 к/с на Mac пользователя: p95 времени кадра CPU меньше 8 мс, и GPU тоже меньше 8 мс.
5. Размер основного бандла без ассетов (атласы, overview, Wasm) записан, и каждый крупный кусок обоснован.
6. Снимки всех видов из `frames.json` сохранены, отличия от эталона перечислены. Оставшиеся отличия либо исправлены, либо названы с причиной.

## 10. Правила работы

- Эталон только читать.
- Комментарии, документация в коде и сообщения коммитов — на английском. Каждый файл `.rs`, `.ts`, `.wgsl` начинается с заголовка:
  ```
  // Copyright (c) 2025-2026 Artem Bobkin.
  // SPDX-License-Identifier: MIT
  ```
- Не коммитить ключи, токены и секреты.
- **Не коммитить и не пушить.** Работа остаётся в рабочем дереве, коммитит пользователь.
- Если решение затрагивает контракт (формат архива моделей, формат PMTiles, данные на `tiles.immersivemap.dev`) или требует от сайтов клиента особых условий, остановиться и спросить пользователя.
- Заглушки и «потом допишу» не оставлять. Если функция не готова, она указана в `docs/STATUS.md` как незавершённая с причиной.
- `docs/STATUS.md` обновляется после каждого этапа: что сделано, что измерено, что осталось.

## 11. Решения пользователя

1. Коммиты агент не делает.
2. Имя npm-пакета: `@immersive-map/web`.
3. Все ассеты (атласы, overview-архив, Wasm, модель дерева, SDF pins) поставляются внутри npm-пакета. Внешнего CDN для них нет. Архивы тайлов и моделей по-прежнему читаются по URL.
